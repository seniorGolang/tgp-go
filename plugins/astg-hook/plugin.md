# Плагин astg-hook — сохранение модели в локальную БД

## Назначение

Post-плагин: после того как в пайплайне появилась модель проекта (обычно от `astg`), сохраняет её **полный снимок** в локальную базу контрактов. Дальше ту же версию подставляют через `astg-db` и `from-db` — без повторного разбора исходников.

Своих CLI-опций нет. Учитывается только наличие `from-db` в запросе (тогда сохранение пропускается).

## Когда использовать

- Один раз разобрали репозиторий — дальше генерируете по сохранённой версии в другом репо/CI.
- Фиксируете поверхность контрактов ветки или тега для сравнения и воспроизводимых сборок.
- Готовите ref вида `ключ@версия` / `ключ:Контракты@версия` для потребителей.

Не имеет смысла снапшотить каждую черновую правку без причины версионирования.

## Что получается / как работает для пользователя

1. В пайплайне есть `astg` и `astg-hook`; hook выполняется **после** появления `project`.
2. При успехе в индекс пишется/обновляется запись `(projectKey, version)` и файл полного снимка.
3. Повтор с тем же ключом и версией **перезаписывает** запись (ветка — мутабельный идентификатор, не immutable release).
4. Если в том же запуске передан `from-db`, hook **молча выходит** — чтобы не затереть загруженную из БД версию локальным разбором.

Проверка записи:

```bash
tg astg json --from-db <ключ>@<версия> -o .tg/saved.json
```

Считайте успехом именно успешный read-back, а не отсутствие ошибки генерации.

## Идентификатор в базе

| Источник | Ключ проекта | Версия (приоритет) |
| -------- | ------------ | ------------------ |
| Git remote | нормализованный URL → sanitized key (`host.org.repo`) | **тег → иначе ветка → иначе `default`** |
| Git есть, remote пустой / непригоден | fallback на module path | то же правило версии |
| Нет Git | module path (слэши → точки; односегментные могут стать `local.<name>`) | `default` |

`--contracts` у генераторов на снимок **не влияет**: сохраняется всегда полная модель, которую положил `astg`.

## Ошибки и silent skip

Hook **не сохраняет**, если:

- в запросе нет `project`;
- в запросе есть `from-db`;
- не удалось вывести непустой project key.

Сбой root/index/write/save — **best-effort**: логируется на уровне **debug** и **не валит** пайплайн генерации. После важного разбора всегда проверяйте БД через `astg-json --from-db` (при необходимости включите debug-логи хоста).

## На что обратить внимание

- Skip при `from-db` намеренный: загрузка из БД не публикует «новый» снимок.
- Ветка как версия перезаписывается при каждом успешном hook на той же ветке — для релиза предпочитайте git tag.
- `--contracts` у `tg server` / clients **не** уменьшает сохранённый снимок: в БД всегда полный проект.
- Успех генерации ≠ успех записи в БД; acceptance — read-back через `astg-json`.
- Ключ в ref должен совпадать с тем, что hook реально записал (нормализованный remote), а не с «коротким» именем репозитория наугад.
- Не редактируйте вручную файлы снимков и индекс.

## Ограничения

- Нет пользовательских опций (только реакция на `from-db`).
- Не загружает и не фильтрует модели — только persist.
- Зависит от того, что `astg` (или другой поставщик) уже положил полный `project`.
- При отсутствии Git remote и module path запись может тихо не состояться (пустой key).

## Связь с другими плагинами

Зависит от `astg`. Потребитель снимков — `astg-db`. Инспекция — `astg-json`. Документация: `tg plugin doc astg-db`, `tg plugin doc astg-json`.
